# Task: Refactor Zephyr UART Async RX into a Standalone Fuzzing Target

## Context and objective

Isolate the UART asynchronous receive logic in the repository's `uart_async_rx.c` for deterministic, userspace fuzzing. Preserve meaningful buffer-management and receive-state behavior while replacing hardware, interrupt, DMA, device-tree, and RTOS dependencies with bounded software equivalents. Integrate it with `harness_uart.c` and the existing `zephyr_compat.h` where appropriate. Do not assume file paths or APIs: inspect the repository first and report what actually exists.

This is a fuzzing-only adaptation, not a production UART driver. Do not alter the upstream source in place; work on a copied standalone target and identify the resulting path.

## 1. Static pre-audit

Inspect the upstream UART source, existing compatibility header, harness, and build configuration before editing. Report:

- The actual source path, driver API, callbacks, receive events, and relevant state transitions.
- Whether the source uses interrupt-driven UART (`uart_fifo_read`, IRQ configuration), asynchronous UART events (`UART_RX_BUF_REQUEST`, `uart_rx_buf_rsp`), DMA-specific APIs, or a combination. Do not assume that asynchronous UART necessarily uses DMA or that ISR APIs are present.
- Existing `extern` declarations and function signatures in `harness_uart.c`; how the harness supplies bytes and whether state resets between fuzz iterations.
- Required data types, error constants, structure members, logging macros, and any Zephyr symbols missing from `zephyr_compat.h`.
- Buffer ownership, event ordering, corner cases, and any timeout or polling loops that could hang without hardware.

Give a `READY TO GO` or `ADJUSTMENTS REQUIRED` assessment for each support file and list exact discrepancies. Do not fabricate hardware or Zephyr APIs absent from the actual source.

## 2. Required modifications

### 2.1 ISR abstraction with a software FIFO

Where the source uses hardware interrupts or FIFO reads, remove or isolate `IRQ_CONNECT`, `irq_enable()`, `irq_disable()`, register access, and hardware ISR wiring. Introduce a bounded software FIFO, for example `sw_fifo_t`, with explicit capacity, head/tail state, and a count or unambiguous full/empty convention.

Make the receive path consume bytes sequentially from this FIFO in place of hardware reads. The harness must enqueue fuzz-generated bytes into the FIFO. Preserve the driver's relevant event and state ordering. If the actual module has no hardware FIFO/ISR interface, adapt its real receive path rather than inventing one.

Specify a deterministic overflow policy (reject or truncate) and ensure no writes beyond capacity or stale data across iterations.

### 2.2 DMA interaction replacement with static buffers

Where applicable, remove hardware DMA configuration, peripheral registers, scatter-gather descriptors, and DMA callback dependencies. Use a static double-buffer pool, sized to match the actual receive requirements (for example, `static uint8_t g_dma_pool[2][256];`). Rotate buffers deterministically and respect buffer ownership, valid lengths, request/response ordering, and bounds. Transfer bytes from the simulated FIFO into the active pool buffer with bounded copies or byte ingestion. Do not replace unrelated allocations solely to force a DMA design when the source does not use DMA.

### 2.3 Logging redirection

Replace Zephyr logging dependencies with lightweight, valid C logging shims: route `LOG_ERR`, `LOG_WRN`, and `LOG_INF` to `printf` or `fprintf(stderr, ...)`; silence `LOG_DBG` to reduce fuzzing overhead. Ensure formatting works with the actual macro call sites, including any zero-argument cases, and avoid conflicting definitions with `zephyr_compat.h`.

### 2.4 Header and device-tree decoupling

Remove or isolate native Zephyr kernel, device, UART driver, logging, and other unavailable headers identified by inspection. Include only needed standard headers, such as `<stdint.h>`, `<stddef.h>`, `<stdbool.h>`, and `<string.h>`, plus `zephyr_compat.h` where needed. Replace or remove `DEVICE_DEFINE`, `PM_DEVICE_DT_DEFINE`, `DT_INST_*`, and related registration/device-tree expressions only when present. Keep compatibility declarations minimal and layout-correct for the code being built.

### 2.5 Bounded polling and timeout behavior

Identify loops waiting for peripheral flags, line idle, or buffer readiness. Replace simulated waits with deterministic progress where feasible; otherwise cap iterations with a named limit such as `UART_MAX_POLL_ITERS 4096U`, and return or transition on timeout. Ensure all input-dependent loops terminate, even for empty, oversized, or malformed inputs. Do not rely on wall-clock delays or nonadvancing hardware flags.

### 2.6 Harness entry points and iteration reset

Provide a compatible, callable C API:

```c
void uart_mock_inject(const uint8_t *data, size_t len);
void uart_mock_process(void);
```

If the audited harness already has a different contract, reconcile its declarations and calls explicitly; document any signature changes. On each fuzz iteration, reset FIFO indices, buffer slots and valid lengths, driver state, event/callback state, and timeout counters. Enqueue the input safely, then process it through the same receive logic used by the standalone target. Handle `NULL` with nonzero length, empty input, exact-capacity input, and overflow deterministically. Do not retain a pointer to harness-owned input after returning.

## 3. Build and validation

- Compile the standalone source, harness, and compatibility layer with the repository's actual build command using standard GCC or Clang and strict warnings (`-std=c11 -Wall -Wextra -Wpedantic`; use `-Werror` if the project supports it).
- Attempt a cross-build with `arm-linux-gnueabihf-gcc` if installed. Explain any missing toolchain or project-specific dependencies instead of claiming success.
- Exercise empty input, a single byte, a normal receive sequence, exact buffer/FIFO boundaries, oversized input, buffer rollover, and repeated independent iterations.
- If available, run AddressSanitizer/UndefinedBehaviorSanitizer builds and document the commands and findings. Check that polling cannot hang and buffer writes stay within capacity.
- Distinguish successful compilation, linking, execution, and sanitizer verification; report actual output or diagnostics for each.
